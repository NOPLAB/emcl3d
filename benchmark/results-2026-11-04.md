# 2コア性能改善の測定結果

最終版は2コア・50粒子・2000点で、最終150更新すべてが100 ms未満。
ラウンド中央値の中央値64.318 ms、p95の最大88.280 ms、最大92.828 msだった。
性能値はx86 Dockerでのコア処理であり、ARM実機やROS全体の周期の測定値ではない。

## 条件

- Windows上のDocker/Linux amd64、AMD Ryzen 7 8840U環境。
- `daifuku-autonomous:humble`、GCC 11.4、PCL 1.12、Eigen 3.4。
- `RelWithDebInfo`、`num_threads=2`、CPU affinity `0,2`。
- 改善前の基準は`5095ffaf0f0126adefb1af52340418da444149f1`。
- 地図は外部の`map_tsudanuma.pcd`（491,004,034 bytes）。
- 50粒子、50点／2000点。入力生成・ウォームアップ・対象外範囲は
  [実行手順](README.md)を参照。
- 保存済みの改善前・改善後バイナリを`base1 → tune1 → base2 → tune2`で実行。
  各実行5ラウンド×30更新、各実装・各点数で合計300更新。

## 反復と負荷の所在

1. 最初の改善は`Map::distance()`の2個のvectorをスレッド別に再利用した。
   2000点の中央値はラウンドごとに238～249 msで、十分な改善は見られなかった。
2. この版で固定問い合わせを区間計測すると、2000点×50粒子の
   `contains()`が0.382 ms、距離探索が150.136 msだった。
   尤度評価で繰り返す最近傍探索が主な負荷と判断した。
3. PCLの問い合わせラッパーを外し、同じfloat XYZ・leaf size 15・
   epsilon 0のFLANN KD-treeへ直接問い合わせるようにした。
   結果バッファはスレッド別に再利用する。
   また、alphaが正常なときの支持判定を省き、成立した粒子があれば走査を終了する。
4. 改善後の固定問い合わせでは、2000点×50粒子の距離探索が
   tune1で54.144 ms、tune2で58.159 msになった。
   第2改善の2つの変更を個別には切り分けていないが、
   範囲判定と探索の区間時間には大きな差がある。

区間計測は更新処理とは異なる固定問い合わせであり、更新時間の厳密な内訳ではない。
第1改善と最終比較の間には時刻による負荷変動もあるため、
最終効果は交互比較の表を基準にする。

## 検証と適用範囲

改善前・改善後ともビルドはexit code 0。
`ctest --output-on-failure`はコア・ROSの2ターゲットとも成功した。
既存のテストはスレッド数による推定・乱数列の一致、膨張リセット、
リサンプリング、ROS入出力などを含む。`git diff --check`も成功した。

この結果はx86のコア処理ベンチマークであり、Raspberry Piの速度や
実走行の精度を示すものではない。2000点では改善後も約115 msを要する。
DDS、TF、前処理、publishを加えた10 Hz動作は保証できない。
ROS実機への反映、daifuku側の依存更新、コミット・pushは行っていない。

## 追加調査: 100 ms未満に向けた厳密探索

前節は最初の測定時点の記録。前節の変更はその後`2c4484a`で
`perf/two-core-query`へpushし、Humble CI成功を確認した。

同じ2000点・50粒子の5回ウォームアップ後の座標から100,000問い合わせを固定し、
KD-treeの葉サイズを比較した。表は5ラウンドの中央値（ms）。
すべての問い合わせの距離二乗をleaf 15の結果配列と直接比較し、
leaf 4、8、24、32、48、64の全ラウンドで完全一致した。

| 葉サイズ | 距離探索 |
| --- | ---: |
| 4 | 256.870 |
| 8 | 173.064 |
| 15 | 182.244 |
| 24 | 146.442 |
| 32 | 133.886 |
| 48 | 128.145 |
| 64 | 127.450 |

コンパイルはGCC 11.4の`-O2`、計測はCPU 0,2の2コア。
別コアでビルドを並行しているため、この表は候補の選別用であり、
前節の更新時間と直接比較しない。計測順によるキャッシュ・周波数変動も含む。
大きい葉は木の走査を減らす一方、葉内の線形探索を増やす。
48と64の差は小さいため、この比較だけで厳密な最適値とは断定しない。

## 採用構成: 4点同時計算の距離専用BVH

葉サイズ、問い合わせの並べ替え、nanoflann、1点のXYZをSIMD化する案は、
実更新の中央値が概ね110～150 msで目標を安定して満たさなかったため不採用。
追加のライブラリ依存は残していない。

採用版は地図の最長軸を中央値で分割するBVHで、各ノードに実点群のAABBを保持する。
葉は最大32点。4点分のX/Y/Zをそれぞれ連続配置し、Eigenで4点の距離を同時に計算する。
問い合わせ中のヒープ確保と、不要な近傍インデックスの生成をなくした。
XYZ座標やボクセル幅は変更せず、floatの箱判定には保守的な丸め余裕を設ける。
アーキテクチャ固有のintrinsicsは書かず、EigenのSSE/NEON実装を使う。

尤度評価では、Gaussian項がdoubleの加算で完全に丸め落ちる距離から先を枝刈りする。
実際のfloat二乗距離境界を使い、最小の除外距離がinlier閾値以上で、
元と同じGaussian混合式の結果が`z_random`と等しい場合だけ有効化する。
条件を満たさない境界や極端な分散では従来の全域探索へ戻る。
単なる実数式の上限では`std::sqrt(float)`の丸め境界を壊すため、この検証を省略しない。
`RelWithDebInfo`のコアも`-O3`とし、`-ffast-math`や`-march=native`は使用しない。

同じ2コア、50粒子、2000点、地図、5ウォームアップ＋30更新×5ラウンドの初回測定:

| ラウンド | 中央値 ms | p95 ms |
| --- | ---: | ---: |
| 0 | 61.142919 | 78.673092 |
| 1 | 58.595311 | 78.883871 |
| 2 | 66.235176 | 80.349061 |
| 3 | 59.065909 | 71.399861 |
| 4 | 60.088536 | 68.354847 |

ラウンド中央値の中央値は60.089 ms、p95の最大は80.349 ms。
全ラウンドでchecksumは`2345.4296944`、リセット回数は0だった。
この測定中は別コアで変異テストのビルドも行っているため、最終確認は別途行う。

追加回帰テストは、不規則な511点・256問い合わせの全点探索との比較、
探索距離上限、元の全域尤度との比較、float平方根のinlier境界を確認する。
平方根欠落、探索上限無効化、不正な尤度打ち切りを故意に入れ、
対応するアサートが失敗することも確認した。変異は採用しない。

### 最終確認

すべての変異を復元して再ビルドし、コア10件とROSノード4件を含む
`ctest --output-on-failure`の2ターゲットが成功した。
最終計測中はビルドを並行させず、同じCPU 0,2だけで実行した。

| ラウンド | 中央値 ms | p95 ms | 最大 ms |
| --- | ---: | ---: | ---: |
| 0 | 62.613702 | 80.253212 | 92.828339 |
| 1 | 64.318306 | 82.089967 | 87.467533 |
| 2 | 65.402979 | 82.704180 | 83.057040 |
| 3 | 65.079104 | 88.279951 | 89.898127 |
| 4 | 60.742163 | 74.649041 | 76.647311 |

初回と最終で計300更新を測定し、全ラウンドのchecksumは`2345.4296944`、
リセット回数は0で一致した。最大値まで記録した最終150更新では最大92.828 msで、
100 msの目標を満たした。最大値は観測値であり、ハードリアルタイムの保証ではない。

回帰テストの検出力も確認し、不正なBVH枝刈りでは全点探索比較が失敗した。
変異を戻した最終テストはすべて成功した。
ローカルの2 CPU制約下では一度ROSノード生成テストがタイムアウトしたが、
通常のCPU割当と隔離ネットワークで成功した。テストのタイムアウトやアサートは変更していない。
CIはx86_64とARM64の両方でReleaseビルド、コア・ROSテスト、
ベンチマークのビルド、インストール済みlaunchの確認を行う。
